# ARM64 Linux Boot Milestone — 2026-10-22

## Result

All defined boot acceptance scenarios met their expected outcomes. This is
platform bring-up and host-runner verification, not CPU feature validation.

Configuration: Debian 13 genericcloud ARM64 build `20261021-2638`, Linux
`6.12.113+deb13-cloud-arm64`, QEMU 8.2.2, `virt-8.2`/GICv3, Cortex-A72, TCG,
two vCPUs, and 1024 MiB RAM. Runner source revision: `17f71af`.

Elapsed time includes preflight/preparation; the injected QEMU execution deadline
was 2 seconds, and the normal deadline was 300 seconds. These measurements are
host wall time, not DUT performance or cycle-level evidence.

Both final normal boots reported:

```text
architecture: aarch64
online_cpus: 2
kernel: 6.12.113+deb13-cloud-arm64
schema_exit: 0
```

The six checks were clean QEMU shutdown, AArch64 architecture, two online CPUs,
valid cloud configuration schema, matching cloud-init completion marker, and
absence of Python traceback. Each run used a different nonce, fresh disk overlay,
and fresh writable firmware variables. The pristine firmware input hashes matched.
The base-image SHA-512 was rechecked after all runs and remained unchanged.

## Evidence

[Machine-readable results](2026-10-22-boot.json) contain expected/actual statuses
and exit codes, observations, checks, runner source hash, firmware hashes,
serial-log hashes, source revision/dirty state, and local artifact paths. Complete
serial logs, QEMU arguments, copied runner source, and generated boot inputs are
retained locally in those ignored artifact directories. Large guest images,
disks, firmware variables, and private guest-generated keys are not committed.

The verification used `python3 build/verify_boot_milestone.py`, an ignored working
copy of the live acceptance checks. The reusable version is now
`python3 tests/verify_boot.py`; it additionally asserts specific negative-case
diagnostics. Those diagnostics and all final evidence were independently checked
when generating this report. Python syntax checks passed for the fetcher, runner,
and reusable acceptance script. No additional live guest rerun was performed
solely for that file promotion.

Some runs report a dirty checkout because documentation and the acceptance
script were being edited. The report generator checked that every final run's
saved `boot.py` SHA-256 matches the final runner, committed at `17f71af`.

## Bring-up findings

Earlier runs are preserved separately and are not substituted for the final
acceptance results:

- `20261022T193943Z-9ddd02c0`: initial narrow boot check passed, but the NIC-free
  configuration incurred a wait-online failure and cloud-config schema warning.
- `20261022T194410Z-97429171`: QEMU startup failed because an optional virtio NIC
  boot ROM was missing. Disabled that unused ROM rather than adding network boot.
- `20261022T194433Z-9f5616e8`: guest shut down with no readiness report. Schema
  output was redirected directly to the serial terminal; changed to file capture
  followed by explicit output/exit reporting. Precise terminal cause is unresolved.
- Intermediate successful narrow checks exposed shutdown interrupting cloud-init
  and producing a socket traceback. Replaced direct `poweroff` in `runcmd` with
  cloud-init's power-state module and strengthened acceptance criteria. Both
  final runs passed those stronger criteria.

The stock image's headless video-mode, optional initramfs fsck, and SSH-generator
AF_VSOCK messages remain visible. General guest service health is outside this
milestone. Image download verification uses the pinned published SHA-512 over
HTTPS; detached-signature validation is not implemented.
