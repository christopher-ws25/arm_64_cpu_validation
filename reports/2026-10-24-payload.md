# First C/AArch64 Payload Milestone — 2026-10-24

## Result

Built, deployed, executed, and live-debugged a C/assembly test under Debian ARM64
Linux in QEMU. Six fixed addition/NZCV cases passed in both normal runs. A
deliberately corrupted expectation failed as intended, and the same binary
passed again without injection. The original boot-only command also passed.

The DUT configuration and pinned OS image are unchanged from the boot milestone.
Runner/helper source revision for the final runs: `caadcbd`. AArch64 GCC 13.3.0
built a static, non-PIE, debug ELF with text segment at virtual `0x41000000`;
the observed assembly function address was `0x41000af4`.

## Payload observations

The guest verified the deployed binary's SHA-256 before launching it. Its binary
hash was `d2874ca7a72e90c76631659777e9d8e8d12d8278dbb72ca11316d4e624cc6fdd`.
The same binary was used for debug, injection, and recovery; only the invocation
argument changed for injection.

All actual sums and flags matched the fixed vector table in `PAYLOAD_WORKFLOW.md`.
Injection changed only ISA-ADD-006's expected sum from `0xfffffffffffffffe` to
`0xffffffffffffffff`. The actual sum stayed `0xfffffffffffffffe`, NZCV stayed
`0xa0000000`, five other cases passed, and the program returned 1. All original
boot checks still passed, demonstrating that OS success cannot hide a test failure.

## Live GDB evidence

Retained transcripts: [successful session](2026-10-24-gdb-success.txt) and
[initial failed check](2026-10-24-gdb-initial-failure.txt).

The successful transcript shows an EL0 stop at the first instruction with
`x0=1`, `x1=2`, and PC `0x41000af4`. After ADDS, PC was `0x41000af8`, `x0=3`,
and the NZCV bits in CPSR were 0. After MRS, PC was `0x41000afc` and `x3=0`.
GDB emitted the matching nonce-tagged result, detached, and exited 0. The guest
then completed every C case and shut down normally.

The initial attempt, `20261024T075136Z-de01890c` at revision `cb42ac4`, hit the
correct function and ran the C cases successfully but failed its MRS debugger
check. The transcript did not show the expected second-step state. The revision
removes the breakpoint before stepping, locks stepping to the selected vCPU, and
checks exact PC advancement. That revised run passed. The exact cause of the
earlier SMP stop/step behavior has not been isolated, and no CPU defect is inferred.

Debug timeout verification separately confirmed both QEMU and GDB PIDs were
absent, both logs existed, and the temporary Unix socket directory was removed.
One preliminary direct timeout invocation produced TIMEOUT too; the retained
acceptance run above explicitly captured Linux return code 124 through Python,
avoiding ambiguity from PowerShell's nonzero-command exit handling.

## Host checks and evidence

Six protocol unit tests passed: normal/injected records, missing/duplicate
observations, false pass versus measured values, nonzero exit contradictions,
wrong nonce/malformed JSON, and explicit injection metadata. No VM was used for
these host tests.

Live acceptance used `tests/verify_payload.py --debug-result .../result.json`.
It checked the already completed debugger run and then launched failure/recovery
runs. The JSON records debugger-result reuse explicitly; its verifier exit field
is null because the verifier did not launch that original run. The original
launcher was independently observed to exit 0, as recorded above. The timeout
acceptance ran `tests/verify_debug_timeout.py` and exited 0 after asserting the
expected launcher exit 124.

[Machine-readable evidence](2026-10-24-payload.json) includes full case
measurements, build command/compiler, source/binary hashes, run source revisions,
checks, expected failure observations, and serial/GDB log hashes. Each local run
also retains copied runner/helper source, binary/source snapshots, seed inputs,
and complete logs. These generated artifacts are ignored by Git. Some checkout
dirty flags reflect documentation edits; the report generator matched all final
run source snapshots against the executed runner/helper source hashes.

The report generator rechecked every case against the independent fixed sums and
NZCV table, checked the expected one-bit corruption, rechecked process absence,
and verified the base image still matches its pinned SHA-512.

## Limits and next step

This is narrow 64-bit ADDS/NZCV and C/assembly calling-boundary coverage through
Linux. The debugger sees QEMU vCPUs and uses a deliberately fixed virtual code
address; this is not a general Linux process debugger. Static linkage, root UID,
and EL0 execution are intentional for this first payload. No memory-protection,
COW, SMP synchronization, physical coherency, timing, or exhaustive ISA claims
are made.

Next: agree one mmap/mprotect test with an expected child-process fault, retaining
the same explicit pass/fail and failure-evidence approach.
